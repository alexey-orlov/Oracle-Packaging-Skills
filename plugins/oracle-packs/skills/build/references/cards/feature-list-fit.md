# When the feature list does not fit, and its footnotes

**Exit 3** means the tree fits no rung, even a row per category at 7pt, and **nothing was written**. Never retry with smaller type: 7pt is the floor, and the lever is a coarser tree, grouped in the spec, not the type size.

**Put to the owner**, in plain words and with the counts the build printed (the estimated height against the budget; the areas, categories and features; the three largest areas and the five largest categories): which categories to merge, which sibling features to generalize into one capability, which names to shorten. Fix the tree through `/oracle-packs:spec`, then rebuild.

**Footnotes** (`*`, `**`, `***` under the legend) exist only for a tier caveat that changes what the buyer gets: at most three in the document, each 15 words or fewer, the caveat alone, never the feature's name or a description of it. The build warns, without failing, when there are more or one runs long: take those cuts to the owner, fix them in the spec, then build.

**Checks**

1. After exit 3, no retry at a smaller size; the counts quoted are the build's own.
2. The proposal names specific areas, categories and features, never "the tree is too big".
3. The tree and the footnotes change in the spec through `/oracle-packs:spec`, never in the document.

**Good.** "Intake and normalization carry nine features between them; merged into one category they read as three, and the page fits." · `**  file export / import at PoV; API write-back is Integration-tier scope`
**Bad.** "The build exited 3 — I'll rerun it at 6.5pt." · `**  Dispatcher UI (map and table views) — the interface dispatchers use to see and assign work.`

**Changes:** `capabilities[]` and `capabilities[].categories[].features[].note`, through the spec skill.
