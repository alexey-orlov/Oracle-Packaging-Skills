# Showing the owner the work, and what comes back

Governs every review: the research summary, the brief, the pictures, every artifact.

**Before building on it**, check any count or roster the owner states against its source. Text the owner wrote and called complete is layout-only: when it breaks a rule, flag it and propose the change separately.

**Open it, then ask.** A render in the side panel (`SendUserFile`, `display: "render"`) with the editable file attached (`display: "attach"`); a text file in the Files pane (`mcp__ccd_view__show_pane`, pane `file`). Never a claude.ai artifact, the synthetic demo excepted: pack material stays on the machine. In a plain terminal, print the path and a text rendering, and say so.

**The review pack**, short enough for a phone: what was built and where it departs from the brief, with why; everything inferred (from what) or synthetic; the open items (the owner's decisions, inferences, facts with no source) and any check that could not run. Parts by name, never keys or files.

**One question**: approve, change (free text) or stop.

**A change** often arrives as a screenshot and a few words: confirm in one line which block you understood. It goes into the brief through the spec skill's fast path, never into the built file; rebuild, re-check, show the changed part. A numbered reply lists changes, each one made. A second round on one point means the brief is wrong: say so.

**Done** = built from the confirmed brief; checks clean, told in one plain line; every changed page, slide or screen looked at; delivered where the owner can reach it; the approval logged in `<work>/decisions.md` with the file's spec stamp.

**Close the loop**: say in one line what you generalized from a correction and where that rule belongs, so the owner can correct it.
