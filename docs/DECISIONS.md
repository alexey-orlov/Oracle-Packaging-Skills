# Owner decisions the skills implement

Recorded 2026-09-18 from the owner's answers during the preparation. These are the standing rules; the research they came from lives in the owner's personal repo, not here. Rewrite a line when a decision changes; do not append dated updates.

| Topic | Decision | Where it is enforced |
|---|---|---|
| Component count | 12 shared components, signed off in the fixed order problem↔solution → one-liner → ICP → name → verticals → capabilities → workflow → architecture → Oracle products → KPIs → packages | `spec` skill, `signoff-flow.md` |
| Tier vocabulary | One set everywhere: PoV Jumpstart / Integration / Scaling; S/M/L only as size tags in internal tables | `lint_spec.py`, `pack-anatomy.md` |
| PoV duration | Per package, ideally 4–8 weeks; 10 weeks hard cap; the skill pushes back with reasons above 8 and refuses above 10 | `pov-rules.md`, `lint_spec.py` |
| Outcome figures | One metric set per pack, from the customer study; attribution varies by approval and channel (named under the customer logo where approved, anonymized otherwise); two different sets for one pack are unacceptable | schema `kpis`, `lint_spec.py`, `check_consistency.py` |
| Features | Area > Category > Feature with ● available / ◐ partial / ○ roadmap; the feature list is the master; the site's workflow-stage view is derived per pack | `feature-list` skill, `listing` skill (`derive-stage-view`) |
| Oracle products | Picked from one shared catalog with canonical names; required = built on it or fully relies on it; optional = could logically be a source or destination; mostly expressed as a per-item flag inside the architecture stack | `shared/data/oracle-products.yaml`, `lint_spec.py` |
| Pack name by channel | Site: plain name; internal exec slide: name + "App"; external one-pager and deck: plain name with an optional "Accelerator App by SoftServe" subheading | schema `meta.name_variants`, `naming-and-clearance.md` |
| Integration claims | State the tier next to every integration claim (file export / import in the PoV, API integration in the Integration tier) | `spec` sign-off card 9, `deck` and `one-pager` skills |
| Standard artifact set | The five artifacts plus the executive summary slide; demo video and Marketplace package/listing are part of a pack's end state but not built by the skills yet; no separate internal scoping one-pager (the feature list plays that role) | `build` skill, `PLAN.md` |
| Sales one-pager | One A4 page, always; overflow means cuts proposed to the owner, never smaller type | `one-pager` skill, `build_one_pager.py` |
| Contacts | Partner print: the alliances contact and mailbox as printed on the existing one-pagers; site: the practice mailbox with the same person named; internal: the person doing the packaging, with the R&D request mailbox | schema `contacts`, `naming-and-clearance.md` |
| Delivery model | Standalone GitHub repo as a plugin marketplace with two plugins (`oracle-packs`: spec + documents; `oracle-packs-web`: listing + demo); pilot as a plain copy first; run the plugin spike before relying on marketplace installs | `README.md`, `PLAN.md` §7 |
| Interaction style | Every proposal comes with a brief exec-level TLDR and grounding plus a question widget; the skill asks the user to locate raw inputs and answers a predefined question list, skipping what the context already answers; when something essential is missing it asks rather than invents; the whole brief is confirmed before building; artifacts are built sequentially with a review pause after each; a demo asks for sources first | `spec`, `build`, `demo` skills |
| Talking to the owner (2026-09-22) | Three rules for everything the owner reads. (a) A widget option is one choice, never a bundle; more than four choices → several questions in one widget call, split along a real boundary. (b) Comparable options are shown first as one table — a column per option, a row per attribute — and the widget then carries only the pick, one plain line per option. (c) Every question, option, card, table, review pack, closing message and document the owner reads assumes no knowledge of the method, the skills or agents, and full knowledge of the delivered engagement and the pack: no research or test ids, no file or key names, no packaging vocabulary, no status glyphs as counts — reasons, not rule names. | `shared/references/talking-to-the-owner.md`, cited and self-checked by all eight skills; `signoff-flow.md`, `intake-questions.md`, `generalization-method.md` §5, `research-brief-format.md`, `review-loop.md` |
| Generalization | The crucial step: the generalized workflow is defined with the domain (how the job is done across industries, how the delivered case differs), a vendor and competitor study, vertical differentiation with adjudication, general enough but not too general; research results come as a very structured TLDR, then one or more name · one-liner · problem↔solution options for the user to pick or send back for more research | `generalization-method.md`, `research-brief-format.md` |
| Deck fidelity (2026-09-22) | The sales deck is built by filling the Workforce Optimization reference deck's own slides, never redrawn; a deck linter checks fonts, header ("Oracle AI & Data Solutions — <pack>"), no tier eyebrow, corner geometry, icons on the verticals, architecture naming and flows, and type floors before the owner sees it; the architecture diagram is derived from the spec under naming and flow rules and reviewed by a fresh-context reviewer; icons and photos come from curated assets the owner picks, never invented | `docs/DECK-FIDELITY.md`, `deck` skill, `lint_deck.py` |
| Problem statement — tangible (2026-09-22) | The problem sentence names a role and a situation with the nouns on that person's desk, and that person could say it about their own week; categories standing in for the nouns fail ("commercial teams work out what a development means for their accounts" → "account managers can't keep up with the market signals, insights and updates in their accounts"). The solution sentence passes the same test from the other side: what that person now does, never the machinery | `cards/story.md`, `pack-anatomy.md` §1 |
| Reader of record — zero context (2026-09-22) | The problem, the solution and the one-liner are written for the Oracle or SoftServe seller who will pitch the pack and has never worked in the industry: the business named, literal words, everything it refers to introduced, cause and consequence, under about 30 words. Where the pain is obvious only to insiders, one clause first says it exists and why it hurts. Tangible but insider-only fails | `cards/story.md`, `pack-anatomy.md` §1–2, `research-brief-format.md` |
| One-liner — the three questions (2026-09-22) | A one-liner answers, in order: of what (the object, named in the buyer's terms) · so what for the business (the outcome in money, time or risk) · how, in one clause, generalized. Every qualifier is tested against "does the claim survive if this customer's circumstance differs?" — if it does, the qualifier goes ("the photos a customer already sends", "the rule that applies in that country") | `cards/story.md`, `pack-anatomy.md` §2 |
| Pack name — noun-led (2026-09-22) | The name names the thing, not the job: a noun phrase a buyer would put on a purchase order ("Damage assessment", "Workforce optimization"), never a verb phrase or imperative ("Repair or replace"). The simplicity test stands — a seller outside the industry needs no briefing | `cards/story.md`, `pack-anatomy.md` §4 |
| Workflow — 5 to 7 steps (2026-09-22) | The workflow is grouped at the buyer's checkpoints, five to seven steps, hard cap seven; mechanics (normalization, dedup, entity resolution, routing, outcome capture) live inside a step's description and are never steps of their own | `cards/workflow.md`, `pack-anatomy.md` §7, `lint_spec.py` (SPEC019) |
| Oracle products — the cap (2026-09-22) | Required is only what the pack cannot run without — the platform as one entry plus the one or two products the core executes on, typically 1–3; infrastructure sub-services are named on the architecture's infrastructure layer, not as entries. Optional holds only what a typical buyer would plausibly connect as a source or destination, typically 2–4. A catalog sweep is cut | `cards/oracle-products.md`, `pack-anatomy.md` §9–10, `lint_spec.py` (SPEC021, SPEC022) |
| Propose before you ask (2026-09-22) | A question is the last resort. Where the inputs or the research answer it, state the answer with its source and move on; ask only where a wrong guess would force a rebuild rather than an edit. The run the owner rated best asked almost nothing and then put three complete alternative pack stories side by side; the run rated worst asked at every step. `/oracle-packs:spec` is capped at 12 questions for a whole run | `cards/owner-language.md`, `spec` SKILL.md, `talking-to-the-owner.md` |
| Cards and the context budget (2026-09-23) | A skill's runtime instructions are per-step cards of at most 300 words — what the part is, the 3–6 checks a draft must pass, one good and one bad example, the spec keys it fills — listed per step in `references/cards/manifest.yaml`; a rule has one home, and rationale lives here, not in the cards. Caps: 6,000 tokens for the start-up set, 2,000 per step, 1,200 words per SKILL.md. The spec skill's start-up read went from 14 files / ~52,000 tokens to 3 files / ~2,600 | `docs/CONTEXT-BUDGET.md`, `shared/tools/context_budget.py`, `run_tests.sh`, `spec` skill |
