# Owner decisions the skills implement

The owner's decisions and why they were made, first recorded 2026-09-18 from the owner's answers during the preparation. The research behind them lives in the owner's personal repo. Rewrite a line when a decision changes; never append a dated update. Where a rule is enforced is the business of the cards and the tools that carry it, not of this file.

| Topic | Decision |
|---|---|
| Component count | 12 shared components, signed off in the fixed order problem↔solution → one-liner → ICP → name → verticals → capabilities → workflow → architecture → Oracle products → KPIs → packages |
| Tier vocabulary | One set everywhere: PoV Jumpstart / Integration / Scaling; S/M/L only as size tags in internal tables |
| PoV duration | Per package, ideally 4–8 weeks; 10 weeks hard cap; the skill pushes back with reasons above 8 and refuses above 10 |
| Outcome figures | One metric set per pack, from the customer study; attribution varies by approval and channel (named under the customer logo where approved, anonymized otherwise); two different sets for one pack are unacceptable |
| Features | Area > Category > Feature with ● available / ◐ partial / ○ roadmap; the feature list is the master; the site's workflow-stage view is derived per pack |
| Oracle products | Picked from one shared catalog with canonical names; required = built on it or fully relies on it; optional = could logically be a source or destination; mostly expressed as a per-item flag inside the architecture stack |
| Pack name by channel | Site: plain name; internal exec slide: name + "App"; external one-pager and deck: plain name with an optional "Accelerator App by SoftServe" subheading |
| Integration claims | State the tier next to every integration claim (file export / import in the PoV, API integration in the Integration tier) |
| Standard artifact set | The five artifacts plus the executive summary slide; demo video and Marketplace package/listing are part of a pack's end state but not built by the skills yet; no separate internal scoping one-pager (the feature list plays that role) |
| Sales one-pager | One A4 page, always; overflow means cuts proposed to the owner, never smaller type |
| Contacts | Partner print: the alliances contact and mailbox as printed on the existing one-pagers; site: the practice mailbox with the same person named; internal: the person doing the packaging, with the R&D request mailbox |
| Delivery model (revised 2026-09-24) | Standalone GitHub repo as a plugin marketplace with **one** plugin, `oracle-packs`, holding every skill and the one `shared/` folder they read. The first cut shipped two plugins (`oracle-packs-web` for the listing and the demo), which forced a synced copy of `shared/` into each plugin, because an installed plugin cannot read files above its own root; the owner chose one plugin on 2026-09-24 |
| Interaction style | Every proposal comes with a brief exec-level TLDR and grounding plus a question widget; the skill asks the user to locate raw inputs and answers a predefined question list, skipping what the context already answers; when something essential is missing it asks rather than invents; the whole brief is confirmed before building; artifacts are built sequentially with a review pause after each; a demo asks for sources first |
| Talking to the owner (2026-09-22) | Three rules for everything the owner reads. (a) A widget option is one choice, never a bundle; more than four choices → several questions in one widget call, split along a real boundary. (b) Comparable options are shown first as one table — a column per option, a row per attribute — and the widget then carries only the pick, one plain line per option. (c) Every question, option, card, table, review pack, closing message and document the owner reads assumes no knowledge of the method, the skills or agents, and full knowledge of the delivered engagement and the pack: no research or test ids, no file or key names, no packaging vocabulary, no status glyphs as counts — reasons, not rule names. |
| Generalization | The crucial step: the generalized workflow is defined with the domain (how the job is done across industries, how the delivered case differs), a vendor and competitor study, vertical differentiation with adjudication, general enough but not too general; research results come as a very structured TLDR, then one or more name · one-liner · problem↔solution options for the user to pick or send back for more research |
| Deck fidelity (2026-09-22) | The sales deck is built by filling the Workforce Optimization reference deck's own slides, never redrawn; a deck linter checks fonts, header ("Oracle AI & Data Solutions — <pack>"), no tier eyebrow, corner geometry, icons on the verticals, architecture naming and flows, and type floors before the owner sees it; the architecture diagram is derived from the spec under naming and flow rules and reviewed by a fresh-context reviewer; icons and photos come from curated assets the owner picks, never invented |
| Problem statement — tangible (2026-09-22) | The problem sentence names a role and a situation with the nouns on that person's desk, and that person could say it about their own week; categories standing in for the nouns fail ("commercial teams work out what a development means for their accounts" → "account managers can't keep up with the market signals, insights and updates in their accounts"). The solution sentence passes the same test from the other side: what that person now does, never the machinery |
| Reader of record — zero context (2026-09-22) | The problem, the solution and the one-liner are written for the Oracle or SoftServe seller who will pitch the pack and has never worked in the industry: the business named, literal words, everything it refers to introduced, cause and consequence, under about 30 words. Where the pain is obvious only to insiders, one clause first says it exists and why it hurts. Tangible but insider-only fails |
| One-liner — the business value (revised 2026-09-29) | A one-liner leads with the specific business value (time, money, risk or capacity) for a named role and object of work, in the buyer's words; any how is what changes in that person's work, in plain words. It never names the platform, vendor, engine, model or data architecture: set on one-liners that read "re-planned on NVIDIA cuOpt" and "from one governed gold layer", with "focus not on the aspects of the tech implementation, but on the very specific business value". The 2026-09-22 form (of what · so what · how, in one clause, generalized) had let the engine stand in for the how. A figure in it is Proven, and it never repeats the tile bullets or the hero line word for word; the site's `oneLiner`, hero line and group line follow the same rule. Every qualifier is tested against "does the claim survive if this customer's circumstance differs?" — if it does, the qualifier goes ("the photos a customer already sends", "the rule that applies in that country") |
| Pack name — noun-led (2026-09-22) | The name names the thing, not the job: a noun phrase a buyer would put on a purchase order ("Damage assessment", "Workforce optimization"), never a verb phrase or imperative ("Repair or replace"). The simplicity test stands — a seller outside the industry needs no briefing |
| Workflow — 5 to 7 steps (2026-09-22) | The workflow is grouped at the buyer's checkpoints, five to seven steps, hard cap seven; mechanics (normalization, dedup, entity resolution, routing, outcome capture) live inside a step's description and are never steps of their own |
| Oracle products — the cap (2026-09-22) | Required is only what the pack cannot run without — the platform as one entry plus the one or two products the core executes on, typically 1–3; infrastructure sub-services are named on the architecture's infrastructure layer, not as entries. Optional holds only what a typical buyer would plausibly connect as a source or destination, typically 2–4. A catalog sweep is cut |
| Propose before you ask (2026-09-22) | A question is the last resort. Where the inputs or the research answer it, state the answer with its source and move on; ask only where a wrong guess would force a rebuild rather than an edit. The run the owner rated best asked almost nothing and then put three complete alternative pack stories side by side; the run rated worst asked at every step. `/oracle-packs:spec` is capped at 12 questions for a whole run |
| Cards and the context budget (2026-09-23) | A skill's runtime instructions are per-step cards of at most 300 words — what the part is, the 3–6 checks a draft must pass, one good and one bad example, the spec keys it fills — named per step on the `Card:` lines of the skill's `SKILL.md`; a rule has one home, and rationale lives here, not in the cards. Caps: 6,000 tokens for the start-up set, 2,000 per step, 1,200 words per SKILL.md. The spec skill's start-up read went from 14 files / ~52,000 tokens to 3 files / ~2,600 |
| Feature list — one page (2026-09-22) | One A4 page is a requirement, not a preference. The capability tree is sized for it at the capabilities sign-off, where the owner is looking at the tree — never at build time, where the only lever left is type size. Type never goes below 7pt; a tree that fits no rung of the fit ladder is not built, and the build reports what has to be grouped |
| Feature list — footnotes and footer (2026-09-22) | A footnote exists only for a tier caveat that changes what the buyer gets: 15 words or fewer, at most three in the document, the caveat alone — never the feature name or a description repeated back, since the marker already points at the row. Nothing in the page footer: the spec version and the build date go into the file's properties |
| Architecture diagram — name the boxes (2026-09-22) | Set on a diagram whose boxes read "Accelerator business app" and "Agentic engine": the app box carries the pack's own name with "by SoftServe", the engine box names the vendor products by their catalog names, sources and destinations are named systems in the buyer's words, and infrastructure is one line naming the services actually used. An unnamed role on a box tells the seller nothing |
| Marketing copy — persona first (2026-09-16) | Set on a customer-facing site's home page whose copy "overemphasized the counts and the scaffolding, not the essence" and used internal vocabulary ("workflow patterns", "packaged") as customer language; on a services page that was "very poorly structured, too long, no grand narrative"; and on a heading that read "From Oracle's platforms to agents in production." — "too long of a heading". Headlines state the job and the outcome in the reader's words; structure is settled before copy; H1 two to four words, H2 five or fewer, budgeted from the rendered size |
| Why the deny-list exists (2026-09-18) | Customer names are the single most likely thing to leak: they sit in the source SoWs, PoC decks, transcripts and spreadsheets a pack is generalized from, and they survive copy-paste. Hence a word-boundary deny-list in one file, extended and never trimmed, plus an independent `grep -ri` sweep over the build output. "Unreferenced is not unshipped": a file inside the publishable root is downloadable by path even when nothing links to it |
| Why references are rewritten, not appended | Two agents once left a reference doc carrying three contradictory verdicts on the same question. Hence: rewrite to current truth, one home per rule, and subagents report a wrong reference rather than editing it |
| Why counts and rosters are verified (2026-09) | "All three use cases" turned out to be four. A stated count or roster is checked against the source of truth before anything is built around it. Equally, silence from a long build is not progress — "alive?" is a failure signal that arrives too late, so long runs write intermediate output early and are checked against the clock |
| Cards for every skill (2026-09-23) | Stage 2 extends the stage-1 card rule to every skill: a per-step card list, ≤300-word cards, ≤6,000 tokens at start-up and ≤2,000 per step, ≤1,000 words per SKILL.md. `run_tests.sh` runs `context_budget.py` on every skill it finds |
| Deck cover hero (2026-09-23) | "The title slide image can be shared across the packs." The cover hero lives on the deck layout and stays unless `deck.images.cover` names the pack's own picture, which is swapped in centre-cropped. An ink-only cover is an unfinished state, never the default. The reference pack's customer logo is still always removed |
| Deck slide order — the revised ten (2026-09-22) | The built deck is cover · use case · vertical applications · today → tomorrow · proof · why it sells for the partner's seller · solution layers · architecture · service packages · service packages detailed. It supersedes the delivered reference estate's order (technology stack on 6, architecture on 7, three package-table alternates on 8–10, no dedicated "why it sells" slide) |
| Pictures — the cover is not a standard slot (2026-09-23) | The deck's cover carries the pack family's shared picture, so `/oracle-packs:visuals` asks for a cover only when the owner wants one of this pack's own. The standard slots are an icon per industry and the today / tomorrow pair |
| Proof slide — the delivered case (2026-09-23) | Set on a pack built from a delivered engagement whose proof slide carried no customer logo, an empty stat band, relabelled quadrants and the pack's own generalized copy — the owner: use the delivered customer's "logo and the specifics of their use case on slide 5. It should adhere to the template from WfO as much as possible." So slide 5 is the delivered engagement in the reference's composition — the customer's logo when their name is cleared, that engagement's own specifics (their sources, their scale, their team), the reference's four labels CONTEXT · SOLUTION · VALUE FOR ORACLE + NVIDIA · VALUE FOR CLIENT in that order, and three stat tiles that are never empty: the cleared figures, else the metrics being measured with their baselines. The slide is only as strong as its clearance, so where the brief has a delivered case the clearance question is **asked, never defaulted**, and proposed as yes for our own team and for Oracle and SoftServe sellers; the logo is owner-supplied from the engagement materials and never searched for (a trademark is not an openly licensed picture) |
| Architecture diagram — one model, three levels (2026-09-23) | "We create an architecture diagram for the deck, for the one-pager and for the mini-site, and they are slightly different in content and visually. Make sure we don't create it from scratch each time — just detail it to the right level. Visually I like the one-pager's layout the most." So: one model per pack, built from the brief's inputs, stack, outputs, products, catalog and the workflow's human step by one function (`build_diagram.build_model`) that all three renderers call, so it is never stored — a stored copy went stale and drew another pack's systems on a deck (2026-09-24); the three renderings — the deck's slide 8, the one-pager's strip (the reference composition), and the site figure generated by `diagram_to_site.py`. Levels of detail are the contract: `name` prints everywhere, `line` on the deck and the one-pager, `detail` only on the site. One reviewer pass, in `/oracle-packs:build` before the deck, on the one-pager's strip — the deck's own diagram-reviewer step is dropped — and `check_diagram.py` asserts every artifact still draws the model, exactly |
| Metrics — the business test (2026-09-23) | Set on the DHL sales one-pager, whose stat tiles read "Reviewer agreement ↑ · Confidence calibrated · Coverage ↑" — proof-of-value acceptance criteria typeset as outcomes. The owner: "metrics should be real business metrics they're impacting (if not articulated — then they should be), not technical criteria of the PoV … specific, but not technical-sounding; clear to someone outside the industry." So every metric passes five tests in order — **business** (already tracked, or fit for a quarterly review: money, time, volume, risk, quality, in the buyer's words), **direct lever** (the solution moves it, not a chain of assumptions; a proxy is `kind: leading`, never the headline), **outsider** (understood in one reading), **owner** (a named buyer-side role signs it off: `owner_role`), and **articulate when the inputs do not** (a proof of value usually defines only technical criteria — derive the business metrics they serve, mark the figures modelled or "results to follow", and put the derived set to the owner). `kpis[].kind` is `business` \| `leading` \| `technical`, defaulting to `business`. Sales artifacts print `kind != technical` on their tiles and chips; technical criteria are routed to the PoV package's success line, "Proof accepted when …", on the deck's packages slides, the one-pager's packages table and the executive summary's tier strip — the WfO reference is the target register: "2 days → 30 minutes to plan · up to +26% productivity · €190K/month saved" |
| The delivered case, and the retired family name (2026-09-23) | Same review, two more corrections. **The proof block** — "I don't really like the DHL case block. Compare it with the WfO reference: the block should speak about the problem and solution for them (not 12 weeks, engagement, all those operational matters)." So the four blocks are about the customer's business: CONTEXT their situation and pain, SOLUTION what they now do, and what each side gains — never the engagement's mechanics (weeks, phases, source counts, contract status, team size, "a proof of value" as a noun phrase), which belong to the footnote (status) or the packages slide (timeline). "A contracted proof of value on NVIDIA AI-Q over OCI" fails; "DHL's account managers cover forty carriers each and learn of a customer's expansion from the trade press, weeks late" passes. **The family name** — "the header at the top says 'OCI accelerators', but we use Oracle AI and Data Solutions — as on the website." The lockup is **Oracle AI & Data Solutions** on every print artifact: refused in the brief's header keys, rewritten by the builders that still meet it, and a finding in any artifact's text on every channel. Oracle's own catalog product `OCI AI Accelerator Packs` is exempt |
| Executive summary — the polish round (2026-09-23) | Set on the DHL executive summary as the DHL case session built it, five findings: the header "PROOF OF VALUE · DHL" plus a line "a proof of value at DHL" was the attribution twice; metric names set in figure type read as numbers; "To be defined" in blue price type read as a price, and stacked twice in one cell as two; no speaker notes said which cut the slide was; CON003 flagged the next step "Run the contracted 12 weeks …" as a tier duration no tier claimed. Which cut carries prices stays with the clearance table (internal and partner cuts every tier, the partner cut with disclaimers); the skill's own text had said "internal only" and now points there instead |

| Cards are capped by the tool (2026-09-23) | The 300-word card rule lived only in prose, and four cards were over it within a day of it being set: a rule that lives only in prose is the rule the next rewrite loses. So `context_budget.py` now counts, file by file, every `.md` a step loads under `cards/` and every `SKILL.md`, and fails the run on a card over 300 words (`owner-language.md`: 400) or a `SKILL.md` over 1,200, naming the file and its count, with `--quiet` too. | Portable by default (2026-09-24) | The plugins have to work on a colleague's Mac or Windows machine, and they silently depended on the owner's Mac: a Python virtualenv only the source checkout has (`.venv/bin/python` or bare `python3` in every instruction), API keys read only from the macOS Keychain, QuickLook and Pages as the only renderers, and agent rules and a permission allow-list that lived only in the owner's personal repo. | The spec in Markdown (2026-09-24) | The owner's decision: one file per pack, `packs/<slug>/pack-spec.md`, read by people and by every builder, replacing `pack-spec.yaml`.
